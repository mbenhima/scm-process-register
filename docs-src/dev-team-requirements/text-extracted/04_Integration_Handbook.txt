1. Introduction & How to Use This Document

This handbook collects, in one document, every technical detail an
external system needs to integrate with the platform. Every endpoint,
event topic, table, control, risk, and field in this document traces
back to a specific source deliverable in the D01–D32k governing set (46
deliverables total, including the D32 series added to close gaps against
Functional Specification v1.3).

1.1 Document Organization

-   Sections 2–4 cover architecture, tenancy, and identity — read once,
    before any integration work begins.

-   Sections 5–8 are the technical reference: API surface, events,
    connectors, and the canonical data model.

-   Sections 9–12 cover licensing, rate limits, governance, and
    internationalization — consult per deployment.

-   Appendix A is a single consolidated endpoint table for quick lookup
    or import into API-testing tooling.

-   Appendix B is the glossary of every ID pattern used across this
    handbook.

2. Integration Architecture Overview

The platform packages 18 licensable modules (D26) across 4 tiers. Every
integration surface is gated by module tier — an integrator's available
endpoints are a direct function of which modules the customer's license
activates. Twelve additional specifications (D32-D32k, covering
infrastructure, WBS/Gantt, phase governance, and two AI-engine
specifications) are not separately licensable — they are cross-cutting
architecture that Module 18 (WBS & Gantt) and Module 19 (Macro Process,
SIPOC, RACSI & End-to-End Registry) already license as part of the
Professional tier.

3. Multi-Tenancy & Data Isolation

3.1 Tenant Hierarchy

The platform's tenant hierarchy is Group (optional) → Organization →
Project. This is the same structure that scopes role-based access — a
role granted in one Organization or Project never grants visibility into
another (see Section 4).

3.2 Isolation Guarantee

CTRL-008 — Role x Scope Least-Privilege Enforcement (D04) — is the
platform's isolation control: it verifies that permissions are always
the product of role × scope, never a single global role, and that a role
assigned in one Project never grants visibility into a different
Project's data. Tested quarterly, automated.

3.3 Risk: Unauthorized Data Access

RISK-011 — Unauthorized Data Access / Privilege Escalation (D05) —
carries an inherent score of 20, mitigated to a residual score of 6 by
CTRL-007, CTRL-008, and CTRL-014 (Data-Visibility Aggregation for
Sponsor/Executive Roles). Detection is automated and continuous.

3.4 Integration Safety Note

Any integration credential (API key, service-account token) is scoped to
exactly one Organization and, where applicable, one Project. An
integrator should never request or expect a credential with cross-tenant
reach — if one is issued, treat it as a CTRL-008 test failure and report
it.

4. Authentication, Identity & Access for Integrators

4.1 Roles Available for Integration Service Accounts

The platform defines ten roles (Section 3.2 of the functional
specification): Super Admin, Group Admin, Organization Admin, Project
Sponsor, Change Manager/Lead, Program/Project Manager, People
Manager/Coach, Practitioner/Contributor, Employee/End User, and
Executive Viewer. Integration service accounts should be provisioned
against the narrowest role that satisfies the integration's actual
read/write needs — never Super Admin.

4.2 Permission Matrix (CTRL-007)

Every page-access, write, and delete check across the platform reads
from one runtime-configurable Permission Matrix grid — a Super Admin can
adjust an integration service account's capabilities without a code
deployment. This is the same control that governs human user access;
integrators are not a special case.

4.3 Service Account Pattern

-   Provision a dedicated account per integration, scoped to
    Organization or Project level — never share a human user's
    credentials.

-   Grant only the capabilities the integration exercises (e.g., Read on
    Risks, Write on WBS Tasks) — verify against the Permission Matrix
    before go-live.

-   Enable MFA/SSO where the account has any write capability (CTRL-009
    — MFA/SSO Enforcement for Administrative Roles).

6. Event & Webhook Interface

6.1 Retry & Resilience Policy

The platform's exception-handling pattern (documented in D02's worked
example, and reused throughout D03a's Retry_Policy field) is exponential
backoff with a bounded maximum attempt count — e.g., 3 attempts on a
validation failure before escalation, 2 attempts on a remedial-training
retry. Webhook delivery should follow the same pattern: exponential
backoff, capped retries, then a dead-letter queue rather than silent
drop.

7.1 Integration Patterns by Category

PPM / Data Warehouse Integration

The REST API (IFC-12) is the general-purpose integration point for both
categories: PPM tools typically consume WBS/schedule data (read/write);
data warehouses typically consume report/dashboard exports (read-only,
scheduled or on-demand).

AI Provider Integration

IFC-13 (Provider Connection Panel) is a special case: it's an outbound
integration where the platform calls an external LLM provider, not an
inbound one. Credentials are isolated to browser-local storage
(CTRL-016) and never transit the platform's own backend.

9. Licensing & Entitlement Interface

9.1 The .lic License Record Schema

For OnPrem deployments, the platform validates against a signed local
license file rather than a cloud record. Every field:

{

"version": 1,

"companyId": "comp_123",

"companyName": "Acme Corp",

"hardwareId": "CPU-ABC123-MAC-DEF456",

"expiryDate": "2027-06-17T23:59:59Z",

"maxUsers": 10,

"plan": "enterprise",

"features": ["analytics", "export", "api"],

"issueDate": "2026-06-17T00:00:00Z",

"signature": "abc123def456..."

}

9.2 Platform Validation Summary — SaaS vs. OnPrem

  -----------------------------------------------------------------------
  Aspect            SaaS                       OnPrem
  ----------------- -------------------------- --------------------------
  Validation target Cloud API / database       Local signed .lic file
                    record                     

  Signing algorithm HMAC (server-side)         Ed25519
                                               (client-verifiable)

  Customer installs Nothing — browser or       Application + one .lic
                    app-store access           file

  maxUsers          Security rules + API on    App logic on every
  enforcement       every write                authenticated request
  -----------------------------------------------------------------------

9.3 Entitlement Evaluation Flow

-   1. License → validate signature and expiry

-   2. Features → check the requested capability against the license's
    features array

-   3. Rate Limit → check the tier's daily API budget (Section 10)

-   4. RBAC → check the requesting account's role x scope permission
    (Section 4)

9.4 Troubleshooting

On a 403 or 429 response, check GET /api/license/check first — the
majority of integration failures in early deployments trace back to an
expired license, an exhausted rate-limit budget, or a feature not
included in the current plan, not a code defect.

12. Internationalization & Multi-Currency Considerations

12.1 Localized Fields

Object classes carrying human-readable text expose a
Multi_Language_Supported flag (D09) — 18 of 35 classes are localized. A
tenant sets a Default_Language (Section 3.1.1); individual users may
override it in-session, but the override never persists across tenants
(CTRL-018).

12.2 Currency

KPI and financial fields carry an explicit KPI_Currency (D06) — MAD is
the reference-market default; the field is present specifically so
integration payloads never assume a fixed currency.

12.3 AI Channel Locale Handling

AI Use Case Library outputs (D15) inherit the requesting user's or
tenant's locale by default — an integrator invoking an AI-assisted
endpoint on behalf of a user should pass that user's locale explicitly
rather than relying on a server-side default.
